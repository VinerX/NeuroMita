- [x] **2. У установки нет прогресса.** (msg `1522731511`)
  **Найдена настоящая причина:** регулярка `RE_PREP` в `pip_installer.py`,
  которая парсит вывод **uv** `Preparing packages... (X/Y)`, была повреждена —
  `\(` и `\)` превратились в литералы `KATEX_INLINE_OPEN/CLOSE` (артефакт
  markdown/KaTeX-конвейера), поэтому детерминированный прогресс uv никогда не
  ловился → вечное «Ожидание данных о размере пакетов». Исправлено:
  - восстановил `RE_PREP` → `\((\d+)\s*/\s*(\d+)\)`;
  - `overall_percent()` / `has_confident_progress()` теперь берут прогресс из
    счётчика «Preparing (X/Y)», когда uv не отдаёт байтовые размеры (частый
    случай) — бар двигается;
  - в сводке не пишем «Σ 0/0», когда прогресс идёт по счётчику подготовки.
  Тот же артефакт чинил в `voice_action_windows.py` (2 ETA-регулярки).
  **Плюс стадийный прогресс по вехам uv** (`Resolved/Prepared/Installed`,
  regex `RE_RESOLVED/PREPARED/INSTALLED/AUDITED`): стадии resolving→preparing→
  installing→done, полосы 0–10 / 10–90 / 90–100, подписи «Скачивание и
  подготовка пакетов…», «Установка пакетов…», «Установка завершена». Работает
  даже без TTY (uv глушит indicatif-бары при перехвате в пайп, но строки-вехи
  печатает всегда) — `RE_PREP` оставлен как более точный источник, когда он есть.
  Проверено: юнит-тесты (6 passed) + симуляция реальной последовательности uv
  (бар 12→32→90→92→100). Живьём на 166-пакетном прогоне не гонял.
  Ресёрч: машинно-читаемого прогресса у uv нет (astral-sh/uv#3199), парсинг
  вывода — единственный путь; вехи выбраны как TTY-независимый драйвер.
